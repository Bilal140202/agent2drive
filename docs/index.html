01

Why paste-back (and not a redirect server)

Google pins the OAuth redirect to http://127.0.0.1:53682/ — on the user's machine. The agent runs headless in a sandbox, a different machine entirely. A tunnel can't intercept it; a redirect server would be extra attack surface. So the flow goes through the one channel both humans and agents share: the chat.

STEP 1

url

The script prints a consent URL — rclone's published default client, narrowest scope Google offers (drive.file).

STEP 2

The user clicks Allow

"Google hasn't verified this app" → Advanced → Go to rclone (unsafe) → Allow. Expected for a public client.

STEP 3

Paste the address bar

The browser "fails" on 127.0.0.1 — copy that full URL (it now carries the code) and paste it back. connect does the rest.

Why the browser "fails": it isn't failing — Google is redirecting to an address that only exists on the user's own machine. That failed page is the expected path; the URL in the address bar is the deliverable. The code is single-use and expires in ~10 minutes — exchange it first, before anything else.
02

Slots — where files land

Everything lives under one root folder (AgentDeliveries by default, GDRIVE_ROOT to change it), one folder per project, one category per job. Uploads are verified byte-exact before the script claims success.

03

Security, plainly

Least privilege by design; honest about what is stored where, and how to take it all back.

SCOPE

drive.file only

The agent can only see and manage files it created itself. The rest of your Drive is invisible to it. Revoke any time: myaccount.google.com → Security → Third-party apps.

STORAGE

chmod 600, gitignored, never printed

The refresh token lives in state/rclone/rclone.conf. state/, bin/, .tmp/ are gitignored. No token is ever printed, logged, or committed.

CLIENT

rclone's published default

Open-source constants (client id + obscure-encoded secret), derived from the binary at runtime and validated against Google's token endpoint. Rate-limited and retiring during 2026 — bring your own client for heavy use (rclone's guide is linked in the README).

RESILIENCE

self-restoring

Missing rclone → re-downloaded. Missing client → re-derived. Only the refresh token is irreplaceable locally — and losing it costs one fresh consent click. Nothing on Drive is ever affected.

04

Quickstart

# check status (prints the connect recipe when not connected)
python3 agent2drive.py

# one-time connect: give the user the URL, get the pasted redirect back
python3 agent2drive.py url
python3 agent2drive.py connect 'http://127.0.0.1:53682/?...code=4/0A…'

# then: slots and uploads, verified byte-exact
python3 agent2drive.py init my-project
python3 agent2drive.py upload my-project ./final.mp4 master
python3 agent2drive.py ls my-project
05

FAQ

Why does the browser "fail" after I click Allow?

It isn't failing. Google redirects to 127.0.0.1:53682 — an address that only exists on your machine. The failed page's URL is the code carrier: copy the whole thing from the address bar and paste it back.

Can it see my other Drive files?

No. The drive.file scope makes everything the agent didn't create invisible to it. Uploads land only in GDRIVE_ROOT/<slot>/<category>.

What happens when the sandbox is wiped?

rclone re-downloads and the OAuth client re-derives automatically on the next command. If the refresh token is gone, you click Allow once more — your Drive contents are unaffected either way.

Windows or macOS?

Self-restore downloads the Linux build by default; point RCLONE_ZIP at your platform's zip and everything else works identically.
